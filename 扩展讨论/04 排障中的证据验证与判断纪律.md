# 04 排障中的证据验证与判断纪律

> 定位：从 [[13 备份磁盘占满线上排障与备份脚本修复]]、[[15 NPM跨容器反代502排障实录]]、[[16 Grafana公网暴露触发IO饱和排障实录]]、[[17 Grafana插件自动重装与止血收尾排障续录]] 四次线上排障中，提炼**"如何用证据验证猜测"**的可复用判据集。
> 与 [[03 Linux-IO拥塞排查方法论与proc采样工具集]] 的分工：03 讲"整机 IO 排查的流程、指标口径与工具集"（通用方法论）；本篇讲"看到现象 → 怀疑某个原因 → 用什么命令/指标证实或证伪"（判断纪律与判据手册）。两篇互补，不重复。
> 适用：任何线上排障场景，不限 IO 问题。

## 一、核心模式：假设 → 证据 → 排除/确认 → 记录

排障的本质是**不断提出假设、用证据证实或证伪、缩小可能范围**的过程。每一步都应能回答三个问题：

1. **我现在的假设是什么？**（用一句话说清"我怀疑是 X 导致了现象 Y"）
2. **用什么证据能证实或证伪这个假设？**（具体命令、具体指标、具体阈值）
3. **证据出来后，假设是被排除还是被确认？**（写下结论，不能停在"我觉得"）

**反面教材**：看到 `docker stats` 卡住就猜测"grafana 占了 CPU"，然后去重启 grafana——这是没有验证就动手。正确做法：先看 `top` CPU 行分类（us/sy/wa），再用 `/proc/io` 差值采样定位大户，证据指向 grafana 再动手。

> 16 §6.2 三条方法论的第一条就是"先分类，再定位；不要拿着现象直接找进程"。本篇把这条原则展开成具体的判据。

## 二、趋势与形态判读

### 2.1 load average 三值形态：恶化、持续、恢复

**现象**：`load average` 三个数字，不知道代表什么趋势。
**常见误判**：只看 1 分钟数字，15 分钟高就以为还在恶化。
**验证方法**：比较 1 / 5 / 15 分钟三个值的大小关系。

| 形态 | 关系 | 含义 | 下一步动作 |
|---|---|---|---|
| 恶化中 | `1 > 5 > 15` | 故障刚发生，正在堆积 | 紧急处置 |
| 持续高位 | `1 ≈ 5 ≈ 15` | 积压未排完 | 需干预止血 |
| **恢复中** | **`1 < 5 < 15`** | **已恢复，平均值正在追下来** | **等待，不要急着操作** |

**判据**：看到 `1 < 5 < 15` 不要误判为"还在恶化"——1 分钟已正常，5/15 分钟只是历史均值的滞后效应，再等 10-15 分钟会追下来。
**案例**：[[17 Grafana插件自动重装与止血收尾排障续录]] 步骤 8，grafana 启动后 6 分钟才 302，期间 `load 1.40/9.38/15.49`，判恢复形态、等待是正确选择；强行重启可能再次触发 IO 拥塞。

### 2.2 wa 高 ≠ CPU 瓶颈

**现象**：`top` 显示 CPU 100%。
**常见误判**：按 CPU 占用排序找"谁占了 CPU"。
**验证方法**：看 CPU 行的 `us/sy/wa/hi/si` 构成。

| 构成 | 故障类别 | 定位方向 |
|---|---|---|
| `us` 或 `sy` 高 | CPU 计算瓶颈 | `top` 按 CPU 排序找进程 |
| **`wa` 高** | **IO 等待** | **找读/写盘大户，不是找 CPU 大户** |
| `si/so` 高 | 内存换页 | 找内存大户与 OOM |

**判据**：`wa` 高时所有进程 CPU 占比都很低（都在等盘），按 CPU 排序找不到"元凶"。先看构成再决定路线。
**案例**：[[16 Grafana公网暴露触发IO饱和排障实录]] §2.1，事故现场 `us 1%、sy 2%、wa 95~97%`，归入 IO 拥塞类。

## 三、"没响应"类现象的甄别

### 3.1 静默重定向 ≠ 卡死

**现象**：脚本执行后终端长时间没输出。
**常见误判**：以为进程卡死了，Ctrl+C 中断或反复重跑。
**验证方法**：

1. 看脚本是否用了 `{ ... } > "$OUT" 2>&1` 整段重定向——如果是，终端只在结束时打印路径，"没输出"是正常现象；
2. 跑只读诊断看进程树：`ps -ef | grep <脚本名>`，确认进程还在；
3. 看最新输出文件：`ls -t /root/<脚本名>-*.txt | head -1`，脚本每完成一段就写入文件；
4. 看 `/proc/<pid>/io` 增量，确认进程在读写而非挂起。

**判据**：终端无输出 ≠ 进程死亡。先确认脚本是否静默重定向，再看输出文件和进程状态。
**案例**：[[16]] §6.1 踩坑表；[[17]] 步骤 1，cleanup2 静默执行实际 6 步全成功。

### 3.2 docker 命令卡死：绕过 daemon 走 /proc

**现象**：`docker ps`、`docker stats`、`docker logs`、`docker stop` 卡住不返回。
**常见误判**：反复重敲同类命令，在 daemon 队列堆积。
**验证方法**：docker CLI 全部经 Unix socket 请求 dockerd；daemon 被 IO 队列阻塞时 CLI 会等待。**改走不依赖 daemon 的只读通道**：

| 原 docker 命令 | 只读替代 |
|---|---|
| `docker ps` 找容器 PID | 遍历 `/proc/<pid>/cgroup` 匹配容器 ID 前缀 |
| `docker stats` 看资源 | `/proc/<pid>/io`、`/proc/<pid>/status` |
| `docker logs` | 直读 `/var/lib/docker/containers/<ID>/*-json.log` |
| `docker inspect` | 读 compose 文件与 NPM 规则目录 |

**判据**：一条 docker 命令卡住后，不再连发同类命令；切换 /proc 只读通道继续采集。
**案例**：[[16]] 步骤 2，docker stats/ps 卡住后全程改走 /proc。详见 [[03]] 第五章。

### 3.3 docker stop 卡死：kill -9 绕过 daemon

**现象**：`docker stop` 在 IO 拥塞期卡死，等优雅退出。
**常见误判**：一直等，或反复 Ctrl+C。
**验证方法**：`docker stop` 要经 dockerd → containerd → SIGTERM → 等优雅退出 → 超时 SIGKILL，整条链路阻塞。**直接 `kill -9 $(pgrep -f <进程名>)` 走内核**，不依赖 daemon。

**判据**：SIGKILL 对 D 状态进程不是立即生效（D 状态收不到信号），但内核 IO 调用返回后会执行，最终能杀掉。这是 dockerd 卡死时停掉容器的有效手段。
**案例**：[[17]] 步骤 7，`kill -9 $(pgrep -f grafana)` 成功停掉 grafana，为 mv 备份腾出窗口。

### 3.4 HTTP 000 + Connection reset：服务在启动还是挂了

**现象**：`curl` 返回 `000` + `Connection reset by peer` 或 `Operation timed out`。
**常见误判**：以为服务挂了，立即重启。
**验证方法**：

1. `docker ps -a --filter name=<容器> --format '{{.Status}}'` 看容器状态：
   - `Up X seconds` = 正常运行，可能还在初始化 → 等待
   - `Restarting (X)` = 崩溃重启循环 → 看日志
   - `Exited` = 已停止 → 启动
2. 循环 curl 检测：`for i in 1 2 3 4 5 6 7 8; do sleep 5; curl ...; done`，出现 302 即成功。

**判据**：`docker start` 返回成功后 curl 立即 reset，通常是 HTTP server 还在初始化（docker-proxy 转发进去被 reset）。等启动完成（cleanup2 那次 40 秒、紧急处置那次 6 分钟）自然 302。**先确认容器 Up 没崩，再决定是等待还是看日志。**
**案例**：[[17]] 步骤 7-8，grafana start 后 curl reset，docker ps 确认 Up，6 分钟后 302。

## 四、数据性质判读

### 4.1 累计值 vs 差值：不要被启动以来的计数误导

**现象**：`/proc/<pid>/io` 的 `read_bytes` 显示几十甚至几百 GiB。
**常见误判**：以为进程现在在读几十 GiB/s。
**验证方法**：`/proc/<pid>/io` 是**进程启动以来的累计值**。进程跑了 8 天，累计自然巨大。必须**两轮快照差值 ÷ 窗口秒数**：

```bash
# 第一轮
cat /proc/<pid>/io > /tmp/io1
sleep 15
# 第二轮
cat /proc/<pid>/io > /tmp/io2
# 差值换算
awk 'NR==FNR{a[$1]=$2;next} {print $1, ($2-a[$1])/15/1024/1024 " MiB/s"}' /tmp/io1 /tmp/io2
```

**判据**：定位实时读速大户必须用差值，不能用累计值直接比较。
**案例**：[[16]] 步骤 4，grafana 累计 105 GiB 但实时窗口 45.82 MiB/s。详见 [[03]] §3.2。

### 4.2 read_bytes vs rchar：判读盘机制

**现象**：进程读速高，想知道是代码循环读还是 mmap 缺页。
**常见误判**：一律怀疑代码里有 read() 循环，去查源码。
**验证方法**：比较 `rchar`（read 系统调用读到的字节）与 `read_bytes`（实际从磁盘读入的字节）。

| 观测组合 | 读盘机制 | 下一步检查方向 |
|---|---|---|
| `rchar` ≈ `read_bytes`，`syscr` 高 | `read()` 系统调用循环 | 查代码/脚本是否有大文件重复读取、日志风暴 |
| **`read_bytes ≫ rchar`** | **mmap 缺页冷读** | 二进制/so/插件/数据库文件被映射；查内存压力、页缓存回收、无用文件体积 |

**判据**：`read_bytes` 是 `rchar` 的上百倍时，读盘来自 mmap 缺页（文件被映射进地址空间，访问未驻留页时由内核换入），不是代码循环。据此决定是查代码还是查页缓存/插件体积。
**案例**：[[16]] §2.2，grafana `read_bytes` 是 `rchar` 的 2270 倍，判 mmap 缺页，避免了在代码读循环上白费时间。

### 4.3 子串误报：grep 命中 ≠ 存在

**现象**：`grep <关键词>` 命中某条记录。
**常见误判**：以为该关键词代表的东西（插件、数据源、配置）真实存在。
**验证方法**：裸 `grep` 做的是子串匹配，`tempo` 会命中 `temporary`。必须用：

1. **单词边界**：`grep -wE '\b<关键词>\b'`，避免子串误报；
2. **结构化字段解析**：JSON 用 `jq` 或 Python 解析 `type` / `pluginId` 字段，不靠正文匹配；
3. **全表核对**：先查 `data_source` 表全量记录，确认外部类型在库里根本不存在，再扫仪表盘正文。

**判据**：甄别数据库/配置内容不能用裸关键词 grep；先看结构化字段全量记录，再用单词边界扫正文。
**案例**：[[16]] §7.2.2，`tempo` 命中实际来自图例文案 `FUSE temporary writeback buffers` 的子串，三轮甄别才闭合。

### 4.4 remote_addr：判流量是否经反代

**现象**：后端日志出现外部 IP。
**常见误判**：怀疑反代配置错误把外部流量透传进来。
**验证方法**：核对后端的 `auth.proxy` 配置：

| auth.proxy 状态 | remote_addr 取值 | 外部 IP 出现意味着 |
|---|---|---|
| `enabled = false` | TCP 连接的对端 | **只能是直连后端，不可能是反代透传** |
| `enabled = true` | 可能是 `X-Forwarded-For` 头的值 | 可能是反代透传的真实访客 IP |

**判据**：`auth.proxy` 关闭时，后端日志的 `remote_addr` 就是 TCP 对端。出现外部 IP 必为直连，排除反代透传假设。
**案例**：[[16]] §2.5，grafana `[auth.proxy] enabled = false`，日志境外 IP 只能来自直连 3000，排除 NPM 透传。

## 五、操作时机与顺序

### 5.1 禁用机制先于清理：删了会装回来的东西

**现象**：清理掉某类文件/配置后，重启又自己长回来。
**常见误判**：反复清理，每次都白做。
**验证方法**：清理前先确认有没有**自动恢复机制**：

| 机制类型 | 排查命令/位置 |
|---|---|
| cron 定时任务 | `crontab -l`、`/etc/cron.*` |
| systemd timer | `systemctl list-timers` |
| 应用内置 installer/update checker | 应用启动日志、配置项 |
| 镜像 entryhook / entrypoint | Dockerfile、compose `command`/`entrypoint` |
| 编排工具自动部署 | compose `GF_INSTALL_PLUGINS`、Helm hooks |

**判据**：**先禁用自动恢复机制，再清理，否则等于白做。** 禁用 + 清理两个条件同时满足才彻底。
**案例**：[[17]] §2.1 + 步骤 4，Grafana 11+ backgroundinstaller 每次启动自动下载 18 个插件，删了就装回；必须先 `GF_PLUGINS_PREINSTALL_DISABLED=true` 再清空 plugins。

### 5.2 备份先于变更：备份时机决定回滚意义

**现象**：做了备份但回滚时发现备份的是改后的文件。
**常见误判**：先手动覆盖原文件，再跑脚本"备份"。
**验证方法**：备份必须在变更**之前**执行，此时备份的是原始版本，才有回滚意义。脚本设计应遵循：

```
预检新文件（验证内容/格式）
    ↓ 验证通过
备份原文件（此时还是旧版本）→ 带时间戳
    ↓ 备份完成
用新文件替换原文件
    ↓ 替换完成
再次验证替换后的文件
    ↓ 验证通过
执行变更（重建/重启）
```

**判据**：预检不通过不碰原文件；备份必须在替换之前。如果脚本假设用户已手动覆盖，备份就失去回滚意义。
**案例**：[[17]] 步骤 5，phase1 第一版脚本备份逻辑有漏洞（假设已覆盖），修正后备份放在替换之前。

### 5.3 mv vs tar：IO 压力下的备份手段

**现象**：IO 拥塞期需要备份大目录，`tar` 打包卡死。
**常见误判**：坚持用 tar，卡在那里等。
**验证方法**：比较两种方式的机制与代价：

| 方式 | 机制 | IO 压力下耗时 | 前提 |
|---|---|---|---|
| `tar -czf` | 读取全部文件内容、压缩、写新文件 | 几十秒~几分钟，可能卡死 | IO 正常时标准备份 |
| **`mv` 改名** | 同一文件系统下只改 inode 引用，不搬数据 | **秒级**，不读数据 | **源和目标在同一文件系统** |

**判据**：IO 压力下的紧急备份用 `mv`（同文件系统下秒级）；正常情况仍优先 tar 做标准备份。跨文件系统 mv 会退化为复制+删除，代价等同于 cp。
**案例**：[[17]] 步骤 7，`mv plugins plugins.bak-manual` 秒级备份 429M 目录。

### 5.4 重建容器 vs 数据卷：重建不丢数据

**现象**：担心重建容器会丢失配置/数据。
**常见误判**：不敢重建，坚持在卡住的容器上修。
**验证方法**：`docker compose up -d` / `docker start` 只更换**容器外壳**（进程、网络栈、cgroup），挂载的**数据卷内容不受影响**。

**判据**：配置、仪表盘、数据源、数据库都在数据卷里，重建后完好无损。重建的代价只是启动期间服务短暂中断，不是数据丢失。理解这一点才能放心做重建。
**案例**：[[17]] §2.5，多次重建 grafana，grafana.db、仪表盘、数据源全部在卷 `monitor_grafana-data` 里完好。

## 六、因果与对照

### 6.1 观测到异常 ≠ 因果成立

**现象**：现场观察到某个异常（某进程内存偏高、某网卡 DOWN、某文件较大）。
**常见误判**：把这个异常当成根因，立即去修。
**验证方法**：根因必须能**串起全部主要症状**。把所有主要现象列出来，看这个异常能否解释每一个：

- 能解释全部 → 可能是根因，继续验证；
- 解释不了其余现象 → 先记录、不结案，继续找。

**判据**：单个孤立异常只是候选解释，不是根因。解释不了其余主要症状的异常，先记录、不结案。
**案例**：[[16]] §6.2 ③，docker0 DOWN、NPM 内存波动都是事实，但解释不了"境外 IP 直连 + 75 秒超时 + cleanup 8 分钟"这组核心现象；[[15]] §6.2 ③ 同样的教训。

### 6.2 对照组：两轮采样区分"过渡残留"与"稳态性质"

**现象**：止血/变更后指标仍未完全正常。
**常见误判**：以为止血没生效，立即采取进一步动作。
**验证方法**：相隔一段时间做**两轮采样对比**：

| 第一轮 | 第二轮（间隔 10-15 分钟） | 判定 |
|---|---|---|
| 仍有异常 | 异常消失 | 过渡窗口残留，止血已生效 |
| 仍有异常 | 异常性质相同 | 稳态问题，需进一步整改 |
| 异常加剧 | 异常加剧 | 止血未生效，需重新处置 |

**判据**：不能用一轮快照下结论。止血后的"残留"可能是已建立连接排空、页缓存重建等过渡现象，需要第二轮采样确认性质。
**案例**：[[16]] 步骤 7，安全组止血后第一轮（10:25）仍有境外 IP 残留 + grafana 71 MiB/s，第二轮（14:39）内部超时链停止、读速降到 29.91——区分了过渡残留与稳态冷读。

### 6.3 时间巧合 ≠ 因果：区分触发点与根因

**现象**：做了某个操作（如开启 Force SSL）后故障出现。
**常见误判**：认为这个操作就是根因。
**验证方法**：

1. 这个操作能否解释全部主要症状？
2. 故障是否在操作之前就已存在（只是没被注意到）？
3. 去掉这个操作，故障是否会消失？

**判据**：时间上的先后不等于因果。真正的根因必须能解释故障机制；时间触发点只是让排障在那个时段被注意到。
**案例**：[[16]] §5.3，NPM 强制 SSL 不是根因——它无法解释境外 IP 直连 grafana；扫描器一直在探测，Force SSL 只是时间重合。

## 七、判断纪律红线

综合四次排障的教训，以下红线在任何排障场景都必须遵守：

### 7.1 只读优先，变更后置

排查阶段默认只读命令（`top`、`vmstat`、`free`、`ps`、`/proc`、`ss`、`dmesg`、日志文件）。变更动作（重启、停容器、清缓存、改配置）必须在定位方向明确、证据落盘后执行。**不因为"看着像某某问题"就重启赌一把**——重启会销毁现场证据，也会清掉页缓存让冷读问题看起来"好了"，掩盖根因。

### 7.2 每一步排除一个假设，证据要能写进记录

"我觉得是某某"不算证据，"命令 + 实测输出 + 排除结论"才算。排障记录里每一步都应有：假设、验证命令、实测结果、排除/确认结论。

### 7.3 不凭单一指标下结论

- load 高 → 看三值形态，不只看 1 分钟；
- 进程读速高 → 看 rchar vs read_bytes，不只看 read_bytes；
- curl 失败 → 看 docker ps 容器状态，不只看 HTTP code；
- grep 命中 → 看单词边界与结构化字段，不只看匹配数。

### 7.4 不重复敲已经卡死的命令

一条 `docker stats` 卡住后，不再连发第二条同类命令。记录卡点（哪个命令、什么时间、是否有部分输出），切换只读通道。确认恢复前，不在命令队列堆积停止/重启类请求。

### 7.5 未闭环的疑点单独成章

未闭环的疑点、未执行的整改、未确认的猜测，都要单独记录，不写成已完成结论。复盘笔记里保留"哪一步是推断、哪一步有实测命令支撑"的区分。
