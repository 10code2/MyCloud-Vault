# 03 Linux IO 拥塞排查方法论与 /proc 采样工具集

> 定位：[[16 Grafana公网暴露触发IO饱和排障实录]] 的配套方法篇。16 记录本次事故的完整经过，本篇沉淀**换一台机器、换一个服务仍然成立**的通用排查流程、指标口径与只读工具集。
> 环境：华为云 Flexus · CentOS 7.9 · 2 核 2G · Docker Compose 多容器
> 日期：2026-10-30
> 适用：整机卡顿、`load average` 飙高、`wa` 居高不下、`docker` 命令无响应等场景；CPU 计算瓶颈与内存抖动只做对照区分，不展开。

---

## 一、先分清故障类别：CPU 忙、内存抖、IO 堵

接到"机器卡了"，第一步不是找进程，而是**分类**。三类瓶颈的整机指标特征完全不同，走错方向会浪费大量时间。

### 1.1 三类故障对照表

| 判据 | CPU 忙（计算瓶颈） | 内存抖（换页瓶颈） | IO 堵（磁盘瓶颈） |
|---|---|---|---|
| `top` CPU 行 | `us` 高（用户态），或 `sy` 高（内核态） | `si/so` 高，`wa` 可能偏高 | **`wa` 高**，`us/sy` 都不高 |
| `vmstat 1 3` | `us` 列高，`r` 列高 | `si`/`so` 列非零，`swap used` 持续增长 | `bi` 或 `bo` 列饱和，`b` 列（D 状态）非零 |
| `free -h` | 内存通常正常 | available 极低、Swap 被吃掉 | 内存可能也紧张，但先看磁盘队列 |
| 典型现象 | 单个进程 CPU 占满一个核 | 整机周期性卡顿、响应忽快忽慢 | 命令敲下去半天没回，`docker`/`ssh` 都慢 |
| 定位方向 | `top` 按 CPU 排序 → 进程 | `vmstat` 换页列 → 内存大户与 OOM | `/proc/<pid>/io` 两轮差值 → 读/写大户 |

### 1.2 本次事故的分类过程

16 笔记现场：`us 1%、sy 2%、wa 95~97%`，`vmstat` 的 `si/so = 0`、`b = 13~15`——CPU 不忙、没换页，纯读 IO 饱和，归入第三类。**分类结论决定后续命令路线**：CPU 路线查 `top -H`、内存路线查 `smem`/`ps --sort`，IO 路线才查 `/proc/io` 与 `wchan`。

### 1.3 复合故障的处理

小内存云主机上三类瓶颈会互相转化：内存紧张 → 页缓存被回收 → 缺页冷读增加 → IO 队列变长 → 进程 D 状态堆积 → load 升高。分类时以**最先出现、占比最大**的指标为主线，其他现象记录为放大因素，不要一开始就按复合故障铺开排查。

## 二、整机指标判读

### 2.1 `top` CPU 行逐列口径

```text
%Cpu(s): 30.1 us, 3.3 sy, 66.6 wa, 0.0 hi, 0.0 si, 0.0 st, 0.0 id
```

| 列 | 含义 | 排障指向 |
|---|---|---|
| `us` | 用户态 CPU：应用业务代码消耗 | 高 → 找 CPU 计算大户（算法、压缩、正则、JSON 解析） |
| `sy` | 内核态 CPU：系统调用、中断、上下文切换 | 持续高 → 检查网络/文件系统调用风暴、容器数量过多 |
| `wa` | IO 等待：进程阻塞在磁盘/网络 IO，CPU 空转 | 高 → 走本篇第三章定位磁盘大户 |
| `hi` | 硬中断 | 高 → 网卡/磁盘中断问题，查 `/proc/interrupts` |
| `si` | 软中断 | 高 → 网络包处理、内核任务积压 |
| `st` | 虚拟化偷取时间 | 仅虚拟机/云主机关注，高则宿主机超卖 |
| `id` | 空闲 | 与其他列互补 |

> 注意：`wa` 高**不等于磁盘硬件故障**。它只表示进程在等 IO 返回，排队原因可能是读饱和、写饱和、NFS/网络存储等待、磁盘错误重试。要继续用 `vmstat` 分读/写。

### 2.2 `vmstat 1 3`：三个采样看趋势

```bash
vmstat 1 3
```

输出取**后两行**（第一行是开机以来平均值，会误导），重点列：

| 列 | 含义 | 读饱和特征 | 写饱和特征 |
|---|---|---|---|
| `r` | 运行队列中等待 CPU 的进程数 | 一般不高 | 一般不高 |
| `b` | 处于不可中断睡眠（D 状态）的进程数 | **持续 > 0**，常达十几 | 同左 |
| `bi` | 每秒从块设备读入的块数（块 = 1KB） | 10 万+ 块/秒即 100 MB/s 量级 | ≈ 0 |
| `bo` | 每秒写入块设备的块数 | ≈ 0 | 高 |
| `si` | 每秒 swap-in 换入 | 0 | 0 |
| `so` | 每秒 swap-out 换出 | 0 | 0 |
| `us` / `sy` / `wa` / `id` | CPU 时间占比 | `wa` 高、`us/sy` 低 | 同左 |

- `bi` 与 `bo` 一高一低，区分本次是**读瓶颈**还是**写瓶颈**；
- `si/so` 持续非零，主线转内存换页，回到 1.1 表重新分类；
- `b` 列长期 > 0 说明队列已经堵死，新进程和已有进程都在等盘。

### 2.3 `free -h` 与内存口径

| 列 | 排障含义 |
|---|---|
| `total` | 物理内存总量 |
| `used` | 真正被进程占用的内存 |
| `free` | 完全未使用的内存（通常很小，不代表内存不足） |
| `buff/cache` | 块设备缓存 + 页缓存，进程需要时内核可回收 |
| **`available`** | **真正可分配给新进程的内存**（扣掉不可回收部分），判断内存紧张看这一列 |

小内存主机上 `free` 常年几十 MB 是正常状态；`available` 持续低于 200M 才视为内存压力。Swap 使用率与 `vmstat` 的 `si/so` 结合判断：Swap 用了但 `so` 为 0，只是历史残留，不是当前抖动。

### 2.4 `load average` 的口径与误读

`top` 第一行三个数分别是 1 / 5 / 15 分钟平均负载。它统计的是**处于运行态 + D 状态**的进程数之和，不只是 CPU 占用：

- CPU 忙：load 高由运行态进程贡献；
- **IO 堵：load 高由 D 状态进程贡献**——CPU 空闲，load 照样很高；
- 2 核机器 load 长期 > 2 即过载；负载曲线 1 分钟远高于 15 分钟，说明故障是刚发生的；15 分钟仍高位，说明积压未排完。

本次事故 15:11 快照 `load 54.84 / 57.17 / 43.96`、`wa 96.3%`：load 爆表但 CPU 空闲，正是 IO 队列堆积的典型形态。

## 三、定位 IO 大户：`/proc/<pid>/io` 两轮差值采样

### 3.1 文件字段口径

每个进程目录 `/proc/<pid>/io` 七个字段：

| 字段 | 含义 | 与磁盘的关系 |
|---|---|---|
| `rchar` | 进程通过 `read()`/`pread()` 等系统调用读到的字节数 | 系统调用口径，含命中页缓存的部分 |
| `wchar` | 进程通过写系统调用写出的字节数 | 同上 |
| `syscr` | 读系统调用次数 | 高频小调用循环时此值突出 |
| `syscw` | 写系统调用次数 | 同上 |
| **`read_bytes`** | **实际从磁盘（块设备）读入的字节数** | 真实物理读 |
| **`write_bytes`** | **实际写到磁盘的字节数** | 真实物理写（含脏页回写部分） |
| `cancelled_write_bytes` | 被取消的写回字节数 | 一般忽略 |

### 3.2 为什么必须两轮差值

`/proc/<pid>/io` 是进程**启动以来的累计值**：进程跑了 8 天，`read_bytes` 自然巨大，直接比较会误判。正确做法：

1. 记录第一轮各进程快照；
2. `sleep 15`（窗口内要有真实负载，空闲窗口测出来全是 0）；
3. 记录第二轮快照；
4. `(第二轮 - 第一轮) / 15` 换算 MiB/s；
5. 按差值排序，主源头一目了然。

### 3.3 读盘性质判读：rchar 与 read_bytes 背离

| 观测组合 | 读盘机制 | 下一步检查方向 |
|---|---|---|
| `rchar` ≈ `read_bytes`，`syscr` 高 | `read()` 系统调用循环 | 进程代码/脚本里是否有大文件重复读取、日志风暴 |
| **`read_bytes ≫ rchar`** | **mmap 缺页冷读** | 二进制/so/插件/数据库文件被映射；查内存压力、页缓存回收、无用文件体积 |
| `write_bytes` 持续高于 `wchar` | 脏页批量回写 | 写缓存策略、日志量、数据库 fsync 频率 |

本次 Grafana `read_bytes` 累计是 `rchar` 的上百倍，直接判定 mmap 缺页，避免了在代码读循环上白费时间。

### 3.4 常用只读命令集

```bash
# 1. 找当前读/写最活跃的进程（需要 sysstat；本机未装则用 /proc 差值法）
# pidstat -d 1 3

# 2. 不依赖 pidstat：列出进程与命令名，配合 /proc/io 差值
ps -eo pid,ppid,comm,args --sort=-pid | head -30

# 3. 查看进程当前状态与累计 IO
cat /proc/<pid>/io
cat /proc/<pid>/status | grep -E 'State|VmRSS|Threads'

# 4. 按 RSS 内存排序（找内存大户，辅助判断页缓存压力）
ps -eo pid,comm,rss --sort=-rss | awk 'NR==1 || $3>10240'
```

### 3.5 容器场景：先从 PID 反查容器

容器进程在宿主机 `/proc` 下与普通进程并列，`ps` 看到的是容器内主进程；要知道它属于哪个容器，读 cgroup：

```bash
cat /proc/<pid>/cgroup
# 输出含 docker-<容器完整ID> 或 /docker/<容器ID前缀>，取前 12 位与 docker ps 对照
```

IO 拥塞期 `docker ps` 卡住时，这是唯一可靠的归属通道（详见第五章）。

## 四、进程在等什么：D 状态、wchan 与内核日志

### 4.1 D 状态（不可中断睡眠）

`ps` 状态列中：

| 状态 | 含义 |
|---|---|
| `S` | 可中断睡眠，等事件（socket、信号量、定时器），正常 |
| `R` | 运行中/运行队列 |
| **`D`** | **不可中断睡眠，卡在内核 IO 调用上**（磁盘、NFS、块设备），信号无法打断 |
| `Z` | 僵尸进程，父进程未回收 |

IO 拥塞现场应统计 D 状态进程：

```bash
ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/'
```

D 状态分散在多个进程 → 全局队列堵；集中在单个进程 → 该进程自身触发了阻塞 IO。

### 4.2 `wchan`：进程睡在内核哪个函数

`/proc/<pid>/wchan` 给出当前阻塞在内核函数名，辅助区分等盘还是等锁：

```bash
cat /proc/<pid>/wchan
ps -eo pid,comm,wchan:40 | grep -v '-'
```

常见函数指向：

| wchan 关键词 | 等待对象 |
|---|---|
| `io_schedule` / `wait_on_page_*` / `balance_dirty_pages` | 磁盘 IO / 页缓存 |
| `futex_wait` / `rwsem` / `mutex` | 内核锁 / 用户态锁竞争 |
| `sk_wait_data` / `tcp_recvmsg` | 网络等待，不是磁盘 |
| `do_wait` / `n_tty_read` | 父进程等子进程 / 终端 |

### 4.3 栈与内核日志补充证据

```bash
cat /proc/<pid>/stack          # 内核调用栈（需 root）
dmesg -T | tail -50            # I/O error、ext4 报错、OOM、设备重置
```

- 出现 `I/O error`、`ext4 remount read-only`、`block device timeout`：硬件/文件系统方向，停止应用层排查；
- 出现 `Out of memory: Killed process`：内存方向，记录被 OOM 的进程；
- 本次事故 `dmesg -T` 全部干净，据此排除硬件与文件系统故障。

## 五、daemon 卡死时的只读通道（Docker 场景）

### 5.1 为什么 docker CLI 会卡住

`docker ps`、`docker stats`、`docker logs`、`docker inspect`、`docker restart/stop/start` 全部通过 Unix socket 请求 dockerd。IO 拥塞期 dockerd 自己也要读写状态文件与日志，被队列阻塞，CLI 就在 socket 上等待。**此时反复敲 docker 命令只会在 daemon 请求队列里堆积，不解决问题。**

### 5.2 通道对照表

| 常规操作 | 卡死期只读替代 |
|---|---|
| `docker ps` 列容器 | 遍历 `/proc/*/cgroup`，匹配 `docker-<ID前缀>` |
| `docker stats` 资源占用 | `/proc/<pid>/io`、`/proc/<pid>/status`、`/proc/<pid>/stat` |
| `docker logs <c>` | 直读 `/var/lib/docker/containers/<ID>/*-json.log`（逐行 JSON，`grep`/`tail` 过滤） |
| `docker inspect <c>` | 读 compose 文件 `/opt/cloudlab/<svc>/docker-compose.yml`；NPM 规则读 `/data/nginx/proxy_host/*.conf` |
| `docker port <c>` | `ss -tlnp` 看宿主机监听；容器内网络状态读 `/proc/<pid>/net/tcp` |

### 5.3 cgroup 反查 PID 的脚本思路

```bash
for p in /proc/[0-9]*; do
  pid=${p##*/}
  cg=$(cat "$p/cgroup" 2>/dev/null | grep -o 'docker-[0-9a-f]\{12\}' | head -1)
  [ -n "$cg" ] && echo "$pid $cg $(cat $p/comm 2>/dev/null)"
done
```

得到"PID ↔ 容器 ID 前缀 ↔ 命令名"对照表后，后续 `/proc/io`、`wchan`、日志归属全部基于这张表，不再依赖 daemon。

### 5.4 直读容器 json 日志注意事项

- 文件路径：`/var/lib/docker/containers/<容器完整ID>/<容器完整ID>-json.log`；
- 每行是一个 JSON 对象，`log` 字段为日志原文，`time` 字段为时间戳；
- 日志可能很大，先 `ls -lh` 看体积，再 `tail` / `grep`，不要整文件读入；
- 日志轮转（json-file driver `max-size`）配置见各 compose `logging` 段；未配置时日志会持续增长，本身也可能成为写 IO 来源。

## 六、采样脚本设计（io-snapshot.sh）

### 6.1 设计原则

1. **全程只读**：不重启、不停止、不杀进程、不改配置、不写容器状态；脚本本身只写自己的输出文件；
2. **不调用 docker CLI**：PID 归属走 cgroup 匹配，日志走文件直读；
3. **两轮差值自动换算**：第一轮快照落临时文件，`sleep 15`，第二轮再采，`awk` 算差值与 MiB/s；
4. **证据一次性落盘**：整机指标、进程 IO、内存 Top、端口监听、连接状态、日志尾部、dmesg 分段写入 `/root/io-snapshot-YYYYMMDD-HHMMSS.txt`，下载回传后离线判读；
5. **分段标题清晰**：每个采集段落带标题与时间戳，便于事后定位证据出处。

### 6.2 段落结构（22 段）

| 段 | 采集内容 | 用途 |
|---|---|---|
| 1 | 主机名、时间、内核版本、运行时长 | 现场基准 |
| 2 | `uptime` / load average | 整机负载趋势 |
| 3 | `free -h` | 内存与 Swap |
| 4 | `vmstat 1 3` | 分类判读（bi/bo/b/si/so/wa） |
| 5 | `df -h` | 磁盘空间排除项 |
| 6 | `top -bn1` 快照 | CPU 构成与进程 Top |
| 7 | D 状态进程清单 | 阻塞范围 |
| 8 | cgroup ↔ PID ↔ 命令名对照表 | 容器归属 |
| 9–10 | 第一轮 / 第二轮 `/proc/<pid>/io` | 差值采样原始值 |
| 11 | 差值换算 MiB/s 排序表 | IO 大户定位 |
| 12 | 各进程 RSS 与状态 | 内存大户 |
| 13 | `ss -tlnp` 监听端口 | 暴露面核对 |
| 14 | 3000（目标端口）活跃连接 | 外部直连证据 |
| 15–18 | 目标容器日志尾部、错误关键词、慢请求、remote_addr 统计 | 触发源与超时链 |
| 19 | `dmesg -T` 尾部 | 硬件/文件系统/OOM 排除 |
| 20 | 容器卷体积与插件清单 | 冷读面盘点 |
| 21 | crontab 与备份进程核对 | 排除定时任务抢占 |
| 22 | 脚本运行结束时间 | 窗口闭合标记 |

### 6.3 复用提示

- 换其他主机使用时，修改第 8 段容器 ID 映射表与第 13–18 段目标端口；
- 采样窗口长度按现象调整：稳态排查 15s 足够；怀疑周期性任务（定时器、缓存 TTL）要延长到一个完整周期；
- 脚本必须 LF 行尾、UTF-8 无 BOM；上传后先 `bash -n io-snapshot.sh` 语法检查再执行；
- 输出文件名带时间戳，多次采样互不覆盖，方便前后轮次对照。

## 七、分层排除清单模板（接到"机器卡了"的标准顺序）

按**成本从低到高、证据从整机到进程**排列；每排除一项，在记录里写下命令与实测结果，不跳步。

| 顺序 | 排查项 | 命令 | 排除标准 |
|---|---|---|---|
| 1 | 磁盘空间是否写满 | `df -h` | 根分区有充足剩余空间（>10%） |
| 2 | 是不是内存换页抖动 | `vmstat 1 3`、`free -h` | `si/so = 0`，Swap 未持续增长 |
| 3 | 是否有备份/压缩/打包类重任务 | `ps -eo pid,comm,etime \| grep -E 'tar\|gzip\|zip\|backup\|rsync'` | 无对应进程；crontab 未到执行窗口 |
| 4 | 硬件/文件系统是否报错 | `dmesg -T \| tail -50` | 无 I/O error、设备重置、ext4 报错、新增 OOM |
| 5 | 目标进程是否崩溃重启循环 | `ps -o pid,etime,comm -p <pid>`、容器启动时间 | 进程已稳定运行，非短命反复拉起 |
| 6 | 数据库/日志文件是否膨胀 | `ls -lh` 数据文件与日志目录 | 体积与正常量级相符 |
| 7 | 是否上游服务查询风暴 | 采样该服务 `/proc/<pid>/io` 与日志慢查询 | 读速/请求量与正常基线相符 |
| 8 | 网关/反代配置是否错误 | 读规则文件、配置段、反代目标 | 规则与预期一致，排除误配 |
| 9 | 外部流量是否绕过反代直连后端 | `ss -tnp` 对端 IP、后端日志 `remote_addr` | 连接对端仅内网网关，无外部 IP |
| 10 | 定位真实大户 | 两轮 `/proc/<pid>/io` 差值采样 | 单个/少数进程读速显著高于其余 |

> 模板使用纪律：前 4 项是整机级排除，成本极低、收益高，必须做完再进入进程级；第 5–8 项用于缩小嫌疑范围；第 9–10 项才是定位动作。跳过前四步直接翻进程日志，是新手最常见的时间浪费来源。

## 八、排障纪律

### 8.1 只读优先

- 排查阶段默认只读命令：`top`、`vmstat`、`free`、`ps`、`/proc`、`ss`、`dmesg`、日志文件；
- 变更动作（重启、停容器、清缓存、改配置）必须在定位方向明确、且已有证据落盘后再执行；
- 不因为"看着像某某问题"就重启服务赌一把——重启会销毁现场证据，也会把页缓存全部清掉，让冷读问题看起来"好了"，掩盖根因。

### 8.2 不重复敲已经卡死的命令

- 一条 `docker stats` 卡住后，不再连发第二条同类命令；
- 记录卡点（哪个命令、什么时间、是否有部分输出），切换只读通道；
- 确认 daemon 恢复前，避免在命令队列里堆积停止/重启类请求。

### 8.3 对照组意识

- 定位"单点故障"还是"全局故障"：同一指标取多个已知正常进程/端口对照；
- 定位"过渡残留"还是"稳态问题"：相隔一段时间两轮采样对比，不能用一轮快照下结论；
- 本次 16 笔记两轮复核（10:25、14:39）正是对照组方法：第一轮看到外部 IP 残留，第二轮确认内部超时链停止。

### 8.4 观测到异常 ≠ 因果成立

现场看到的任何异常（某进程内存偏高、某网卡 DOWN、某文件较大）都只是**候选解释**；根因必须能串起全部主要症状（外部 IP、请求耗时、内部任务循环、IO 队列）。解释不了其余现象的异常，先记录、不结案。

### 8.5 证据落盘

- 关键命令输出在事故窗口内重定向到文件，不在终端翻屏中丢失；
- 记录时间戳、PID、容器 ID（PID 会变，容器 ID 不变）；
- 未闭环的疑点与未执行的整改单独成章，不写成已完成结论；复盘笔记里保留"哪一步是推断、哪一步有实测命令支撑"。
